# План развития каталога, объявлений и продавцов — Luna

> **Для агентов:** выполнять по одному пакету с superpowers:executing-plans; координатор использует subagent-driven-development при запуске независимых агентов. Рабочая модель исполнителей — Luna, без самостоятельной замены модели. Этот документ разрешает планирование; реализация и deployment сейчас не запущены.

**Цель:** закрыть пункты 4–25 запроса пользователя, начиная с поиска и контакта с продавцом.

**Архитектура:** расширять существующие FastAPI API, Next.js компоненты и PostgreSQL модели. Использовать единое состояние поиска и существующие saved searches, notifications, billing, SEO; не создавать параллельные реализации. Внешние интеграции включать только при наличии реального провайдера и настроенной среды.

**Стек:** Next.js/React/TypeScript, FastAPI/SQLAlchemy/Alembic/PostgreSQL, Vitest/pytest.

**Спецификация:** требования пользователя от 15.10.2026, пункты 4–25, полностью сопоставлены ниже.

## Ограничения и исходная точка

- Проверено чтением текущей локальной рабочей копии 15.10.2026. Это не аудит production и не доказательство прохождения тестов.
- `main`, origin `https://github.com/TuzVik-bot/avbyartur.git`. Рабочая копия содержит множество изменённых и новых файлов, включая незакоммиченные реализации перечисленных функций. Не сбрасывать и не переносить все изменения одной командой.
- Координатор сначала составляет выбранный baseline с владельцами текущих изменений. Чистый worktree от HEAD сам по себе не содержит нужных незакоммиченных функций. Для каждого пакета нужен проверенный набор зависимостей из baseline.
- Не менять production, Nginx, режим доступа, данные, тома и .env; выпуск — отдельная явно разрешённая задача с rollback и повторной проверкой активного релиза.
- Сохранить регистрацию email, CSRF, ограничения публикации, категории, list/grid на четыре колонки, светлую/тёмную/системную тему, актуальную навигацию.
- Не выдавать слова продавца, административную метку или наличие VIN за проверенную историю. Не придумывать отзывы, статистику, аналоги, доступность оплаты и провайдеров.
- Backend-тесты только в выделенной одноразовой PostgreSQL БД: имя заканчивается `_test`; `TEST_DATABASE_URL` и `TEST_DATABASE_DISPOSABLE_CONFIRMATION` заданы явно. Документированную preview-БД не использовать.
- Общие файлы `models.py`, `listing_schemas.py`, `api/listings.py`, `lib/api.ts`, `lib/types.ts`, `types.generated.ts`, `globals.css` меняются по очереди через координатора. Generated types генерирует один интегратор после изменений API.

## 4. Порядок исполнения и защита от конфликтов

1. **Нулевая волна — координатор:** выбрать и зафиксировать baseline без чужих изменений, проверить migration heads, согласовать API для D/E/G/H/J и контракт saved searches. Сохранить перечень уже имеющихся функций.
2. **Волна 1:** Luna A + B + C. Это максимум три рабочих агента при одном координаторе и лимите четырёх активных слотов. Координатор интегрирует общие контракты последовательно.
3. **Волна 2:** D + E + F. E готовит самостоятельные компоненты; вставки в detail/card только после D/C. Общий route меняет интегратор.
4. **Волна 3:** G + H + J. Перед началом интегратор принимает нужные миграции и контракт событий. H не правит home-search A.
5. **Волна 4:** I и K; интеграция, регрессия, отчёт. Провайдерные задачи могут ждать конфигурации, независимые пакеты продолжаются.
6. **Выпуск:** отдельный запрос; повторный аудит активного VPS-релиза и сохранение параллельных изменений, миграции/backup/rollback, затем настоящие browser/provider проверки.

Никакого одновременного редактирования общего рабочего файла разными агентами. При разных worktree использовать один проверенный baseline и отдельные ветки `codex/<package>`; переносить только собственные коммиты. При общей директории назначать эксклюзивные файлы и последовательные окна интеграции.
