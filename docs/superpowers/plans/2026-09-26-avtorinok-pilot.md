## 2. Техническое и продуктовое ТЗ

### 2.1. Архитектура

Один репозиторий, один модульный бэкенд, одна основная база данных.

| Компонент | Решение P0 |
|---|---|
| Интерфейс | Next.js App Router, TypeScript, React, Tailwind |
| API | FastAPI, Python 3.12, Pydantic |
| Работа с БД | SQLAlchemy 2, Alembic |
| База | PostgreSQL 17 |
| Поиск | PostgreSQL: обычные индексы, нормализованные названия, `pg_trgm` |
| Фоновые операции | Отдельный worker с устойчивой очередью заданий в PostgreSQL |
| Изображения | Закрытый файловый volume; обработка Pillow и pillow-heif |
| Внешний вход | Caddy, HTTPS, единый origin |
| Запуск | Docker Compose |
| Проверки | pytest, Vitest, Playwright |
| Зависимости | pnpm и uv, зафиксированные lock-файлы |

Конкретные совместимые патч-версии закрепить при создании проекта, после установки и smoke-проверки. Не использовать плавающие `latest` в выпуске.

Для первого сервера отдельные Redis, Meilisearch, OpenSearch и MinIO не устанавливать. Интерфейсы поиска и хранения выделить в самостоятельные модули, чтобы позже заменить реализацию без изменения форм и публичного API. PostgreSQL предоставляет индексируемый поиск по сходству строк через [`pg_trgm`](https://www.postgresql.org/docs/17/pgtrgm.html).

Основные правила взаимодействия:

- FastAPI — единственный источник бизнес-правил, прав доступа и переходов состояний.
- Next.js отвечает за страницы, формы и SSR, но не дублирует правила публикации.
- PostgreSQL — источник истины для объявлений, каталога, квот и статусов.
- Worker обрабатывает изображения, обновляет курс и выполняет техническую очистку.
- Задание создаётся в той же транзакции, что и связанная запись.
- Задания имеют попытки, время следующего запуска и аренду исполнения. После падения worker незавершённое задание возвращается в обработку.
- Повторы не создают дополнительные фотографии или повторные побочные действия.
- В P0 одновременно обрабатывается одно изображение; браузер загружает не более двух файлов параллельно.

Объявление после одобрения доступно непосредственно из PostgreSQL: отдельного периода ожидания поисковой индексации в P0 нет.

### 2.2. Автокаталог: происхождение, покрытие и импорт

**Полная актуальная база марок, моделей, поколений и модификаций пока не выгружена.** Её получение — отдельная задача реализации с проверяемым результатом.

Принята гибридная стратегия:

1. Для закрытого пилота — структурированные данные Wikidata CC0 и проверенные ручные дополнения.
2. Для расширенного коммерческого покрытия — лицензированный поставщик после подтверждения условий.
3. Для отсутствующей машины — ручной ввод продавцом с проверкой модератором.

У Wikidata структурированные данные доступны под CC0; это не означает автоматического разрешения использовать любые фотографии Wikimedia. [Условия и способы доступа](https://www.wikidata.org/wiki/Wikidata:Reuse).

Основной коммерческий кандидат — Auto-Data.net. Для хранения каталога в собственной PostgreSQL рассматривать **One-Call**, а не REST-подписку: условия One-Call предусматривают локальное хранение, тогда как постоянное хранение данных REST API запрещено. Для площадки с кабинетами сторонних компаний требуется отдельно подтвердить применимость лицензии к этому сценарию. Покупки и обращения поставщику без разрешения владельца не выполнять. [Условия Auto-Data.net](https://api.auto-data.net/terms-and-conditions).

Car2DB остаётся резервным кандидатом, но не подключается одновременно с первым поставщиком в течение ночной разработки. [Документация Car2DB](https://car2db.com/api/).

#### Структура каталога

```text
Марка
└── Модель
    └── Поколение / рестайлинг
        └── Вариант кузова конкретного поколения
            └── Модификация двигателя / трансмиссии
```

Отдельно существуют общие типы кузова: седан, универсал, хетчбэк и другие. Они не являются дочерними записями одного конкретного поколения.

Для записей хранить:

- собственный стабильный ID;
- русское и исходное название, slug, поисковые алиасы;
- родительские связи;
- годы начала и окончания, когда они подтверждены;
- статус производства: продолжается, завершено, неизвестно;
- рынок или регион применимости, если он известен;
- источник, внешний ID, версию, дату получения и условия использования;
- отметку ручной проверки и защиту ручных исправлений от перезаписи.

`year_to = null` означает отсутствие значения, а не автоматически «выпускается сейчас».

Год выпуска автомобиля, модельный год и годы существования поколения — разные понятия. В объявлении обязательно спрашивается именно год выпуска.

Примеры алиасов: `BMW`, `БМВ`; `3 Series`, `3 серия`, `3er`. Belgee и Geely сохраняются как разные марки.

#### Минимальное покрытие пилота

Технический минимум стартового набора: 25 марок и 50 проверенных моделей. Это критерий стартового наполнения, **не заявление о полноте рынка Беларуси**.

Приоритетные марки:

Audi, BMW, Mercedes-Benz, Volkswagen, Škoda, Renault, Peugeot, Citroën, Opel, Ford, Toyota, Lexus, Nissan, Mazda, Hyundai, Kia, Volvo, Geely, Belgee, Chery, Changan, Haval, BYD, Zeekr, Lada.

Обязательный контрольный набор для глубины и качества:

- BMW 3 Series — поколения, рестайлинги, разные кузова;
- Volkswagen Passat;
- Belgee X50 и X70;
- Geely Coolray;
- BYD Atto 3;
- Zeekr 001.

Для контрольного набора проверяются доступные годы и связи. Неподтверждённые характеристики остаются пустыми. Выдумывать поколения, даты и модификации ради количества запрещено.

Импортировать остальные разрешённые записи можно сверх минимума. Если источник не позволяет подтвердить заявленное покрытие, результат фиксируется как неполный, а не маскируется синтетическими автомобильными фактами.

#### Процесс импорта

`Получение → нормализация → проверка → dry-run с отчётом → применение → отчёт покрытия`.

Обязательные свойства:

- повторный импорт не создаёт дублей;
- новые данные не меняют собственные ID и URL существующих записей;
- ручные исправления сохраняются;
- пропавшие из частичной выгрузки записи не удаляются;
- некорректный пакет не применяется частично без явного решения оператора;
- исходные лицензированные выгрузки не попадают в публичный git или публичный API;
- сохраняются версия импортера и контрольная сумма входного файла.

Отчёт должен показывать количество марок, моделей и поколений, заполненность годов, неизвестные связи, конфликты и происхождение записей.

География строится аналогично: Минск, шесть областей, населённые пункты с источником. Район необязателен. Отсутствующий населённый пункт допускается ввести вручную с проверкой.

### 2.3. Пользователи, компании и вход в пилот

Закрытый пилот имеет два независимых уровня защиты:

1. Парольный барьер на весь сайт, API и изображения.
2. Индивидуальные аккаунты приложения с серверными ролями.

Общий пароль пилота не заменяет авторизацию внутри приложения.

В P0:

- публичная регистрация выключена;
- тестовые аккаунты создаются административной командой;
- пароли хешируются Argon2id;
- сессии хранятся на сервере, токены — в защищённых cookie;
- cookie: `HttpOnly`, `Secure`, `SameSite=Lax`;
- срок сессии — семь дней, с возможностью немедленного отзыва;
- изменяющие запросы защищены от CSRF;
- универсальные OTP и `DEV_AUTH_BYPASS` на VPS запрещены;
- тестовые данные не содержат чужих реальных телефонов, VIN и документов.

Роли: пользователь, модератор, администратор. Право действовать от имени компании определяется принадлежностью к ней, а не ролью, присланной из браузера.

Компания имеет название, УНП, адрес, контакты, владельца и статус проверки. В P0 у компании один управляющий аккаунт; приглашение сотрудников переносится на следующий этап.

Формат УНП проверяется, но сам по себе не даёт отметку «компания проверена». Администратор разрешает компании публикацию вручную. Публичный знак юридической проверки до утверждения процедуры не показывается.

У одобренной компании есть публичная страница со всеми её активными автомобилями.

### 2.4. Объявление и форма подачи

Форма состоит из шести шагов:

1. Продавец и тип предложения.
2. Автомобиль и характеристики.
3. Состояние и условия.
4. Цена, расположение и контакт.
5. Фотографии.
6. Предпросмотр и отправка.

Обязательные данные для отправки:

- частный продавец или одобренная компания;
- марка и модель из каталога либо явно заявленные вручную;
- год выпуска;
- пробег;
- основные технические характеристики;
- состояние;
- цена и исходная валюта;
- населённый пункт;
- контакт;
- минимум одна обработанная фотография.

Поколение, модификация, VIN и комплектация необязательны.

Не смешивать независимые признаки:

- эксплуатация: новый / с пробегом;
- повреждения: отдельный признак;
- цель продажи: целиком / на запчасти.

Таким образом, повреждённый автомобиль может одновременно продаваться целиком или на запчасти.

Основные проверки:

- год выпуска от 1886 до текущего года по серверному времени;
- пробег неотрицательный, цена положительная;
- электрический автомобиль не требует объёма ДВС;
- несовместимые значения справочников не принимаются;
- несоответствие известным годам поколения требует исправления или ручного варианта с пояснением;
- VIN при указании проверяется как формат, но не объявляется доказательством подлинности;
- описание — обычный текст, без HTML и выполняемых вставок.

Черновик автоматически сохраняется на сервере. Интерфейс показывает «сохранено», «сохраняется», «не удалось сохранить». При временной потере сети форма не очищается.

Локальный буфер допускается для нечувствительных полей; телефон и VIN не сохраняются в обычном браузерном хранилище. Неотправленные фотографии требуют понятного повторного действия после перезагрузки страницы.

### 2.5. Статусы, модерация и квоты

Статусы:

`draft`, `pending_review`, `rejected`, `active`, `paused`, `sold`, `archived`, `blocked`.

Правила P0:

- Все объявления проходят премодерацию.
- Отправка фиксирует конкретную ревизию данных и состав фотографий.
- Одобрить можно только текущую отправленную ревизию.
- Первая сохранённая правка опубликованного объявления снимает его с публичного показа и возвращает в черновик.
- После исправлений требуется повторная отправка.
- Возобновление неизменённого, ранее одобренного объявления допускается после проверки квоты и состояния продавца.
- Отклонение и блокировка требуют причины.
- Заблокированные пользователи и компании не сохраняют публичный доступ к своим объявлениям и контактам.
- Администратор не должен незаметно менять текст от имени продавца: изменения аудируются.

Для защиты от гонок использовать номер ревизии и ожидаемую ревизию в запросах. Устаревшее редактирование или решение модератора возвращает `409 Conflict`.

Квоты проверяются транзакционно. Объявления на проверке резервируют место, чтобы два параллельных запроса не позволяли обойти ограничение. Черновики, отклонённые, снятые и проданные записи активную квоту не занимают.

В закрытом пилоте активные объявления автоматически не истекают. Проданная карточка сохраняется 30 дней с отметкой «Продано», без раскрытия контакта; затем архивируется.

### 2.6. Фотографии

Принимать JPEG, PNG, WebP и HEIC/HEIF. Поддержку HEIC проверять на реальных тестовых файлах и целевой архитектуре контейнера; библиотека предоставляет интеграцию с Pillow и бинарные сборки для распространённых систем. [Документация pillow-heif](https://pillow-heif.readthedocs.io/en/latest/installation.html).

Пределы P0:

- 1–30 фотографий на объявление;
- до 20 MiB на файл;
- до 60 мегапикселей после декодирования;
- не более двух одновременных загрузок из браузера.

Обработка:

1. Проверить фактический формат, объём и принадлежность загрузки.
2. Сохранить в закрытый карантин под собственным случайным именем.
3. Декодировать с ограничением ресурсов.
4. Применить ориентацию.
5. Удалить EXIF, включая координаты.
6. Перекодировать в WebP: варианты до 320, 768 и 1600 px без увеличения исходника.
7. Перевести фотографию в `ready`.

SVG, анимации, повреждённые файлы и замаскированные исполняемые данные отклонять.

Публикация невозможна, пока выбранные фотографии не обработаны. Ошибка одного файла не уничтожает остальные.

Оригиналы не публикуются и после успешной обработки удаляются. Зависшие и непривязанные загрузки очищаются через 24 часа. Публичная доступность производных изображений определяется состоянием объявления; знание URL не даёт доступа к чужому черновику.

Смена обложки и порядка выполняется без повторной загрузки.

### 2.7. Поиск, цены и карточка

Обязательные фильтры:

- марка, модель, поколение, тип кузова;
- цена, год, пробег;
- топливо, коробка, привод;
- новый / с пробегом, повреждения, продажа на запчасти;
- область, населённый пункт;
- частник / компания.

Поисковая строка учитывает названия и алиасы марок/моделей. Телефоны и скрытые VIN не участвуют в публичном текстовом поиске.

Сортировки:

- сначала новые объявления;
- цена по возрастанию и убыванию;
- сначала более новый год выпуска;
- сначала меньший пробег.

Пагинация — 25 объявлений. При одинаковом значении сортировки использовать стабильный дополнительный ключ ID.

Все фильтры отражаются в URL. Обновление страницы и кнопка «Назад» сохраняют состояние.

В выдаче показываются только доступные активные объявления. Пустой результат содержит количество, выбранные условия и возможность убрать отдельный фильтр.

#### Валюта

Хранить исходную сумму в `numeric/Decimal` и исходную валюту BYN или USD. Через JSON денежные суммы передавать строками, а не числами с плавающей точкой.

Для пересчёта использовать официальный курс НБРБ с датой и масштабом:

`сумма BYN = сумма USD × Cur_OfficialRate / Cur_Scale`.

Официальный endpoint проверен и возвращает эти поля. Страница общей документации при исследовании отвечала нестабильно, поэтому интеграцию дополнительно проверить контрактным тестом. [Официальный API НБРБ](https://api.nbrb.by/exrates/rates/USD?parammode=2).

Правила:

- обновлять курс ежедневно, при сбое повторять с ограниченной частотой;
- не применять курс будущей даты;
- использовать один подтверждённый курс для всего ответа выдачи;
- отображать дату пересчёта;
- допустимый возраст последнего подтверждённого курса — 72 часа;
- после этого показывать только исходную цену;
- при отсутствии допустимого курса смешанная сортировка и фильтрация по цене недоступны; остальные фильтры работают;
- исходная цена никогда не перезаписывается пересчитанной.

Порядок основного и справочного отображения BYN/USD для публичного выпуска подтверждается юридически.

#### Карточка и контакт

Карточка содержит фотографии, характеристики, описание, цену, расположение, статус, сведения о продавце и ссылку на автомобили компании.

Телефон отсутствует в исходном HTML, общедоступном JSON карточки и JSON-LD. Он возвращается отдельным запросом только после нажатия кнопки и проверки лимитов.

В синтетических данных показывается тестовый контакт без возможности позвонить постороннему человеку.

Избранное доступно после входа. Повторное добавление не создаёт дублей. Проданное объявление остаётся в избранном с соответствующей отметкой.

Жалоба имеет категорию, комментарий и статус рассмотрения. Несколько одинаковых жалоб не скрывают объявление автоматически.

### 2.8. Данные и API-контракты

Основные группы данных P0:

| Группа | Сущности |
|---|---|
| Доступ | Пользователи, сессии, роли |
| Компании | Компании, принадлежность пользователей, решения проверки |
| Каталог | Марки, модели, поколения, типы кузова, варианты кузова, модификации, алиасы |
| Происхождение данных | Источники, импорты, версии, ручные исправления |
| География | Области, населённые пункты |
| Объявления | Объявления, ревизии, фотографии, история статусов |
| Пользовательские действия | Избранное, жалобы, события раскрытия контакта |
| Служебные данные | Курсы, задания worker, настройки квот, аудит |

Не создавать в P0 пустые платёжные, чатовые и дилерские импортные подсистемы.

Объявление хранит ссылки на каталог и снимок характеристик. Изменение каталога не должно задним числом незаметно переписывать опубликованную машину.

Основные группы REST API:

| Назначение | Контракт |
|---|---|
| Каталог | `GET /api/v1/catalog/makes`, `/models`, `/generations`, `/body-types`, `/body-variants`, `/modifications` |
| География | `GET /api/v1/locations/regions`, `/cities` |
| Вход пилота | `POST /api/v1/auth/login`, `/logout`; `GET /api/v1/me` |
| Черновик | `POST /api/v1/listings/drafts`; `PATCH /api/v1/listings/{id}` |
| Состояния | `POST /api/v1/listings/{id}/submit`, `/pause`, `/resume`, `/sold` |
| Фотографии | Загрузка, удаление, порядок и обложка в ресурсах конкретного объявления |
| Выдача | `GET /api/v1/listings`; `GET /api/v1/listings/{id}` |
| Контакт и жалобы | `POST /api/v1/listings/{id}/phone-reveal`, `/reports` |
| Избранное | `GET /api/v1/me/favorites`; идемпотентные `PUT/DELETE` по ID объявления |
| Кабинет | `GET /api/v1/me/listings`; профиль и компания пользователя |
| Компании | Создание и редактирование своей компании; публичные страницы одобренных компаний |
| Модерация | Очереди объявлений/компаний/жалоб и решения с ожидаемой ревизией |
| Состояние системы | `/health/live`, `/health/ready` |

Фото загружаются непосредственно в API, без фиктивной реализации S3 signed URLs.

Ошибки имеют единый формат: `code`, `message`, `field_errors`, `request_id`.

Обязательные ответы:

- `401` — нет действующей сессии;
- `403` — нет права на действие;
- `404` — публичный ресурс отсутствует или недоступен;
- `409` — конфликт ревизии или квоты;
- `422` — некорректные поля;
- `429` — превышен лимит;
- `503` — временно недоступна необходимая зависимость.

Создание черновика, отправка и загрузки защищаются от повторов идемпотентными ключами.

OpenAPI — единый контракт для фронтенда и тестов. Типы клиента генерируются из него; вручную расходящиеся копии схем не поддерживаются.

## 3. Страницы, интерфейс, SEO и безопасность

### 3.1. Карта сайта

Структура страниц и перелинковка определены с использованием site-architecture.

```text
/                                   Главная
├── /cars                           Поиск автомобилей
│   ├── /cars/{make}                Автомобили марки
│   │   └── /cars/{make}/{model}     Автомобили модели
│   │       └── /{id}               Карточка объявления
│   └── /cars/city/{city}            Автомобили в городе
├── /dealers                        Компании
│   └── /dealers/{slug}              Компания и её автомобили
├── /sell                           Начать подачу
├── /account                        Кабинет
│   ├── /account/listings           Мои объявления
│   ├── /account/favorites          Избранное
│   └── /account/company            Моя компания
├── /moderation                     Очереди и решения
├── /login                          Вход
└── /help                           Помощь и документы
```

Поколения и остальные характеристики в P0 работают через фильтры. Отдельную индексируемую страницу для каждой комбинации не создавать.

Верхняя навигация: «Автомобили», «Компании», «Избранное», «Кабинет», основная кнопка «Подать объявление».

Хлебные крошки связывают карточку с моделью, маркой и каталогом. Страница компании связана с её объявлениями. У индексируемых страниц не должно быть отсутствующих внутренних ссылок.

### 3.2. Визуальное направление

Оригинальный mobile-first интерфейс с визуальным ориентиром на светлую, лёгкую композицию Belavia: белая шапка, выразительный синий брендовый акцент, крупный фотоблок и заметная поисковая форма. Перенести эти приёмы на автомобильный классифайд, сохраняя бренд «Авторынок», содержание и пользовательские сценарии проекта; не копировать логотип, фирменные тексты и уникальные элементы Belavia.

- главный экран сразу показывает поиск автомобилей и реальные предложения, а крупная фотография автомобиля поддерживает поиск и не оттесняет его;
- светлая основа, тёмный текст и синий акцент бренда; контрастный дополнительный цвет применять точечно для основного действия;

- семантические цвета ошибок, статусов и предупреждений отделены от брендового синего и цвета основного действия;
- компактные карточки и крупные фотографии;
- минимум декоративных блоков перед поиском;
- читаемые цены и характеристики;
- понятные подписи «Частный продавец» и «Компания»;
- шрифт с кириллицей, без обязательных внешних загрузок;
- размеры элементов управления не менее 44 px;
- видимый фокус, работа с клавиатуры, подписи полей и ошибок.

На телефоне:

- фильтры открываются в отдельной панели;
- активные условия видны над выдачей;
- кнопка контакта не перекрывает содержание;
- фотографии можно переставлять без точного попадания в маленькую область;
- ошибки находятся рядом с полями;
- форма показывает текущий шаг и сохранённость данных.

Проверять ширины 320, 390, 768 и 1440 px, а также увеличение текста до 200%.

### 3.3. SEO-поведение

В пилоте **все страницы закрыты от публичного доступа и индексации**. SEO-поведение будущего публичного режима проверяется локально и в тестах.

| Тип страницы | Поведение после отдельного публичного выпуска |
|---|---|
| Главная и основной каталог | Индексируемые SSR-страницы |
| Марка / модель | Индексация при наличии содержательного каталога и не менее трёх активных предложений |
| Город | Индексация при наличии собственного содержания и не менее десяти предложений |
| Активное объявление | `200`, self-canonical, включение в sitemap |
| Проданное | `200`, явная отметка, `noindex`, исключение из sitemap; через 30 дней — архив |
| Черновик, проверка, пауза, блокировка | Публичный `404` |
| Архив ранее опубликованного объявления | `410`, без перенаправления на главную |
| Произвольные фильтры и сортировки | `noindex`, нормализованный URL |
| Кабинеты и вход | Неиндексируемые служебные страницы |

Дополнительные требования:

- Карточки и выдача содержат основное содержание уже в HTML, а не только после JavaScript.
- Навигация и пагинация используют настоящие ссылки.
- Каждая страница пагинации имеет собственный canonical; страница 2 не канонизируется на страницу 1. [Рекомендации Google по пагинации](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading).
- Разные фильтры не объявляются автоматически дублями основного каталога. [Фасетная навигация](https://developers.google.com/crawling/docs/faceted-navigation).
- URL в нижнем регистре, без завершающего слеша; нормализация через редирект.
- ID объявления стабилен. Изменение канонического пути не создаёт вторую карточку: старый путь перенаправляется на новый.
- Canonical строится из доверенного `SITE_ORIGIN`, не из произвольного входящего заголовка Host.
- Sitemap содержит только канонические индексируемые страницы и реальные даты изменения.
- `robots.txt` не используется как замена авторизации или гарантированный способ удаления из индекса.
- Разметка `Car`, `Offer`, `BreadcrumbList` содержит только подтверждённые видимые данные.
- Не обещать специальный Google Vehicle Listing rich result: Google прекратил его поддержку. [Официальное объявление](https://developers.google.com/search/blog/2025/06/simplifying-search-results).

Изображения имеют размеры, `srcset`, корректные `alt`; первое значимое изображение не загружается лениво, последующие — загружаются.

Целевые Core Web Vitals: LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1. До появления реального трафика можно подтвердить только лабораторные проверки, не полевые показатели 75-го перцентиля. [Описание метрик Google](https://developers.google.com/search/docs/appearance/core-web-vitals).

### 3.4. Безопасность и эксплуатация

Обязательный минимум:

- проверка владельца каждого объявления, изображения и ресурса компании;
- отдельные публичные и приватные схемы ответов API;
- серверная защита контактов и VIN;
- параметризованные запросы;
- ограничения входа, загрузок, подачи, жалоб и раскрытия контакта;
- доверие proxy-заголовкам только от собственного reverse proxy;
- отсутствие секретов в git, HTML, логах и отчётах агентов;
- закрытые порты PostgreSQL, worker и внутреннего API;
- отсутствие публичной раздачи каталогов с файлами;
- отсутствие внешней загрузки фотографии по произвольному URL;
- аудит модерации, блокировок и изменения квот;
- JSON-логи с `request_id`, без полных телефонов, VIN, паролей и токенов.

Начальные лимиты входа — десять неудачных попыток за 15 минут на сочетание IP/логина; раскрытия контактов — 30 в час на аккаунт. Лимит по аккаунту не объединяет пользователей за общим IP web-контейнера. Доверять forwarded-IP и добавлять IP-лимит можно только после проверки цепочки прокси VPS и тестов подмены заголовков.

В P0 не подключать внешнюю аналитику и передачу содержимого объявлений в LLM. Модели используются для разработки, не для обработки пользовательских персональных данных.

Резервирование пилота:

- ежедневный бэкап PostgreSQL и производных фотографий;
- семь ежедневных точек;
- проверка восстановления в отдельную тестовую БД и отдельный каталог;
- целевые RPO 24 часа и RTO 2 часа, подтверждаемые упражнением восстановления.

Копия вне VPS обязательна перед публичным выпуском. Если место для неё ещё не предоставлено, это фиксируется как ограничение закрытого пилота, а не как выполненное промышленное резервирование.

## 4. Организация работы Luna-агентов и график суток

### 4.1. Реальный параллелизм

В текущей среде доступны **четыре активных слота: координатор и три исполнителя**.

Исполнители:

```text
model = gpt-6-luna
reasoning_effort = max
```

Координатор — текущая Astra. Глобальную конфигурацию Codex не менять.

Выбранная Luna уже успешно использовалась для исследовательских задач. Это подтверждает возможность запуска, но не гарантирует отсутствие последующих ограничений API.

M1 Pro с 32 GB не выполняет инференс облачных Luna локально. Ноутбук обслуживает редактор, контейнеры, сборки, браузеры и тесты. Поэтому количество одновременно полезных агентов ограничивается также зависимостями задач, API и локальными проверками.

За сутки можно последовательно сменить несколько специализированных ролей, но одновременно держать не более трёх работников.

### 4.2. Владение кодом

| Исполнитель | Ответственность | Не изменяет самостоятельно |
|---|---|---|
| Координатор | Архитектура, контракты, общие конфигурации, миграции, интеграция, итоговые проверки | Не подменяет отчёты исполнителей предположением о готовности |
| Luna A — домен/API | Вход, сессии, компании, объявления, квоты, поиск, избранное, модерация | Интерфейс, фотообработчик, инфраструктура |
| Luna B — интерфейс/SEO | Все пользовательские страницы, формы, кабинеты, модераторский UI, SSR и метаданные | Бизнес-правила API и миграции |
| Luna C — данные/медиа/эксплуатация | Каталог и импортер, география, курс, фотографии, worker, Docker и резервирование | Пользовательские страницы и правила владения объявлениями |

Разделение директорий закрепить до запуска параллельных изменений. Общие точки подключения роутеров, зависимости, lock-файлы, общие тестовые фикстуры и миграции изменяет координатор.

Каждому агенту передавать:

- конкретный результат и перечень принадлежащих ему модулей;
- зафиксированный контракт;
- сценарии приёмки;
- запрет на откат чужих изменений;
- запрет на самостоятельный деплой, покупки, push и работу с чужими данными;
- требование приложить команды и результаты проверок.

Использовать общий checkout с непересекающимися зонами ответственности. Git-операции и контрольные коммиты централизованы у координатора. Изменение общего контракта сначала согласовывается, затем одновременно обновляются потребители.

### 4.3. Задачи с критериями завершения

| Задача | Владелец | Результат и приёмка |
|---|---|---|
| T0. Основание | Координатор | Проект запускается; БД доступна; миграции проходят с нуля; API и web имеют smoke-тесты |

| T3. Объявления и модерация | Luna A | Черновик → проверка → публикация; ревизии и квоты выдерживают конкурентные запросы |
| T4. Изображения и курс | Luna C | HEIC/JPEG проходят обработку; приватность и EXIF проверены; сбой курса не создаёт ложную цену |
| T5. Подача и кабинеты | Luna B | Пользователь завершает форму с телефона, исправляет ошибки и видит реальные статусы |
| T6. Поиск и карточка | Luna A + Luna B, каждый в своей зоне | Фильтры, URL, SSR, избранное, контакт и страница компании работают вместе |
| T7. Защита и эксплуатация | Luna C + координатор | Полный парольный барьер, закрытые порты, health-checks, бэкап и восстановление |
| T8. Независимая приёмка | Переназначенные review-роли + координатор | Проверки прав, гонок, SEO и сценариев выполнены не только автором соответствующего модуля |
| T9. Выпуск пилота | Координатор | После предоставления VPS выполнены preflight, развёртывание, smoke и проверка версии |

Для бизнес-правил сначала писать отрицательный или граничный тест, затем реализацию. Для интерфейса — компонентные проверки и сквозные сценарии.

Отчёт агента: задача, изменённые модули, выполненные тесты, результат, ограничения, необходимые следующие действия. «Запущено» не равно «завершено», а «проходит локально» не равно «развёрнуто».

### 4.4. Расписание от начала реализации

| Время | Работа | Контрольная точка |
|---|---|---|
| 0–2 часа | Основание, документы, схема, контракты, базовый UI | Web/API/DB запускаются совместно |
| 2–8 часов | Три параллельные линии: домен, интерфейс, каталог/медиа | Каждый модуль проходит собственные тесты |
| 8–14 часов | Сквозная интеграция частника и компании | Первое объявление проходит весь путь |
| 14–19 часов | Права, гонки, файлы, SEO, мобильность, нагрузка | Закрыты критические ошибки |
| 19–22 часа | Выпускные сборки, восстановление, runbook, подготовка VPS | Есть воспроизводимый release candidate |
| 22–24 часа | Развёртывание при доступном VPS и итоговая проверка | Подтверждённый закрытый пилот либо готовый локальный выпуск с конкретным блокером |

Это целевой бюджет, не гарантия готовности при любых внешних условиях.

После 14-го часа новые функции не добавлять. При нехватке времени сокращается декоративная полировка и дополнительное наполнение сверх согласованного минимума; права, премодерация, безопасность файлов и основные пути пользователей не исключаются.

### 4.5. Ограничения ноутбука и управление сбоями

При проверке было свободно около 34 GiB. Это существенное ограничение сборок и контейнеров.

Правила:

- одна общая интеграционная среда;
- не более одной тяжёлой Next.js-сборки одновременно;
- Playwright — максимум два worker;
- один фотообработчик;
- не создавать по Docker-стеку на каждого агента;
- проверять свободное место перед тяжёлой сборкой;
- при остатке менее 15 GiB приостанавливать новые тяжёлые операции;
- при росте memory pressure уменьшать параллелизм тестов, а не менять настройки системы;
- не чистить пользовательские файлы и глобальные кеши без разрешения;
- не менять VPN, маршруты и другие рабочие настройки;
- не запускать локальные модели ради замены облачной Luna.

Для временных ошибок API — ограниченные повторы с увеличением задержки. Ошибки доступа или исчерпания квоты не повторять бесконечно. Сохранять checkpoint и продолжать независимые доступные задачи.

Не менять модель молча при недоступности Luna.

Длительная работа требует питания, сети и доступной сессии Codex. Безлимитный API сам по себе не гарантирует непрерывное выполнение в течение суток.

## 5. Приёмка, VPS и условия публичного выпуска

### 5.1. Обязательные тесты

| Область | Проверяемые сценарии |
|---|---|
| Частный продавец | Вход → черновик → фото → отправка → одобрение → поиск → карточка |
| Компания | Создание → проверка компании → публикация → общий список её автомобилей |
| Квоты | Шестое активное объявление частника и 51-е компании не допускаются; два параллельных запроса не обходят лимит |
| Права | Нельзя читать приватный черновик, менять чужую запись, чужой порядок фото или действовать от чужой компании |
| Ревизии | Модератор не одобряет устаревшую версию после изменения продавцом |
| Состояния | Продажа, пауза, блокировка и повторная проверка корректно меняют выдачу, карточку, контакт и доступность фото |
| Фото | JPEG/HEIC, ориентация, удаление EXIF, повреждённый файл, ложный MIME, превышение размера/пикселей/количества |
| Повторы | Повторная отправка, загрузка и перезапуск worker не создают дубли |
| Каталог | Алиасы, неверные родительские связи, неизвестные годы, ручной вариант, повторный импорт |
| Валюта | Decimal, масштаб, округление, одна дата курса на выдачу, недоступность и возраст более 72 часов |
| Поиск | Комбинации фильтров, сортировки, пагинация, пустая выдача, сохранение URL |
| SEO | HTML без выполнения JS, canonical, пагинация, sitemap, noindex и HTTP-статусы |
| Мобильность | Заявленные ширины, клавиатура, масштабирование, отсутствие горизонтального скролла |
| Восстановление | Бэкап разворачивается отдельно; совпадают записи и доступные фотографии |
| Отказы | Остановка БД/worker даёт корректный статус, а не ложный успешный ответ |

Проверки выполняются на настоящей PostgreSQL, а не на SQLite, подменяющей её транзакционное поведение.

Нагрузочный сценарий для пилота: 10 000 синтетических объявлений, 20 одновременных пользователей, до 20 запросов в секунду в течение десяти минут. Цель для поиска и карточки API — p95 до 500 мс и менее 1% серверных ошибок на согласованном стенде. Фактические параметры стенда и результаты записать; не переносить автоматически локальные цифры на VPS.

### 5.2. Развёртывание

Доступ к VPS пользователь предоставляет после плана. До этого удалённые изменения не выполняются.

Для подключения нужны:

- IP/hostname и SSH-порт;
- отдельный пользователь;
- способ доступа через SSH-agent или установленный публичный ключ;
- подтверждённый fingerprint;
- временный домен;
- параметры CPU/RAM/диска;
- сведения о существующих сервисах;
- выделенное место для резервной копии.

Пароли и приватные ключи в чат не передавать.

Рабочий ориентир закрытого пилота — 4 vCPU, 8 GB RAM и не менее 60 GB доступного SSD. Это исходный бюджет для проверки, а не основание автоматически покупать сервер.

Порядок:

1. Read-only preflight: архитектура CPU, память, диск, порты, Docker, существующие сервисы.
2. Проверка доступа и fingerprint.
3. Выделение отдельной директории и ресурсов проекта.
4. Подготовка сборки для архитектуры VPS; ARM64 ноутбука не считать автоматически совместимой с AMD64 сервера.
5. Настройка секретов вне git.
6. Проверка миграций и резервирования.
7. Запуск с закрытым пилотным режимом.
8. Проверка HTTPS, страниц, API и изображений без пароля и с паролем.
9. Проверка полного пользовательского сценария на развёрнутой версии.
10. Запись версии выпуска, результатов smoke-тестов и процедуры отката.

Если порты или reverse proxy заняты, существующие сервисы не заменять. Изменения общего серверного контура требуют отдельного согласования.

### 5.3. Что считается завершённым результатом суток

Поставка принимается, если:

- основной путь работает для частника и компании;
- отсутствуют неработающие элементы, выдаваемые за готовые функции;
- каталог имеет проверяемое происхождение и честный отчёт покрытия;
- права, квоты, ревизии и фотографии выдерживают отрицательные тесты;
- SEO-основа проверена, но пилот остаётся закрытым;
- проект воспроизводимо запускается;
- выполнена проверка восстановления;
- известна точная версия локального и, при наличии доступа, серверного выпуска;
- остающиеся ограничения перечислены отдельно.

Если VPS ещё не предоставлен, допустим результат «проверено локально, готово к развёртыванию». Он не называется развёрнутым проектом.

### 5.4. Отдельные условия публичного запуска

Публичный выпуск не выполняется простым снятием пароля. До него обязательны:

- работающий провайдер SMS и проверка реального сценария регистрации;
- подтверждённые условия использования автокаталога;
- утверждённые юридические документы, правила обработки данных и хранения;
- согласованные требования к хостингу и отображению валют;
- безопасный доступ администраторов, включая второй фактор;
- резервная копия вне основного VPS и повторная проверка восстановления;
- финальная проверка безопасности;
- явное разрешение владельца на открытый запуск.

Чат, фиды, платежи и продвижение реализуются следующими самостоятельными этапами после работающего ядра. Их отсутствие не должно мешать бесплатной продаже автомобиля через площадку.
