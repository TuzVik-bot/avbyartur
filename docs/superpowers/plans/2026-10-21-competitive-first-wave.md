# Конкурентный аудит Авторынка — первая очередь

> **Для исполнителей:** выполнять только свою зону. Рабочая копия содержит незакоммиченные пользовательские изменения; не сбрасывать их и не заменять файлы целиком. Перед собственными правками повторно проверить `git status --short` и актуальный `origin`.

**Цель:** улучшить первый пользовательский путь по четырём наблюдаемым проблемам: доступ к публичному сайту, свежесть дилерских объявлений, полезный ответ на пустой поиск и возврат пользователя к новым объявлениям через подписки.

**Архитектура:** развивать текущие API, выдачу, dealer feeds, saved searches и inbox уведомлений. Для сравнения использовать отдельный гостевой интерфейс и только публичные объявления. TLS диагностировать снаружи read-only; изменение Nginx, DNS, сертификата, VPS и выпуск остаются за пределами этой очереди.

**Стек:** Next.js/React/TypeScript, FastAPI/SQLAlchemy/PostgreSQL, существующий worker и тестовые стеки проекта.

**Основание:** запрос пользователя на конкурентный аудит и первую очередь; ранее составленный roadmap — `docs/superpowers/plans/2026-10-15-catalog-product-luna.md`.

## Ограничения и контроль

- Не публиковать релиз, не менять VPS, Nginx/TLS, DNS, данные, тома, `.env` и режим доступа.
- Не создавать синтетические объявления и не подключать новые зависимости, платные каналы или выдуманные провайдеры.
- Backend integration tests запускать только с явными `TEST_DATABASE_URL` и `TEST_DATABASE_DISPOSABLE_CONFIRMATION` для отдельной одноразовой PostgreSQL БД с точным именем, оканчивающимся на `_test`; preview-БД запрещена.
- `backend/app/models.py`, миграции, `web/src/lib/api.ts`, `web/src/lib/types.generated.ts` и `web/src/app/globals.css` не редактировать параллельно. Контракты и необходимые общие изменения сначала согласовать с координатором.
- Проверенное наличие исходного кода и тестов не считать подтверждением публичной доступности, доставки на production или роста возвратов.

## Зоны владения

### 1. Публичный доступ и дилерские фиды — `feeds_and_access`

**Файлы:** `backend/app/api/feeds.py`, `backend/app/feed_services.py`, `backend/app/feed_schemas.py`, связанные dealer-feed API tests, `web/src/components/dealer-feeds.tsx` и относящиеся к нему tests. В `backend/app/worker.py` изменений не планировать.

- Повторить TLS/DNS/hostname handshake для `https://suite-s1.denjik.by` и сохранить только read-only доказательства ошибки и границу между внешним TLS и внутренним приложением.
- Проверить существующее создание и импорт dealer feeds, отметку последней успешной синхронизации, частичные/ошибочные загрузки, идемпотентность и безопасную обработку отсутствующих объявлений.
- В первой очереди показывать или улучшать фактическую свежесть и ошибки источника; не импортировать данные и не останавливать объявления на production.

**Приёмка:** воспроизводимый read-only TLS результат; тесты корректного/частичного/ошибочного импорта и повторной синхронизации; видимое время последнего успешного применения и понятная ошибка без показа ключей.

### 2. Сравнение 2–4 автомобилей — `comparison`

**Файлы:** новые compare provider/button/page и их tests; интеграции с `web/src/components/listing-card.tsx` и `web/src/components/listing-detail.tsx` принадлежат этому владельцу. Любые общие API/type изменения — координатору.

- Гостевой список сравнения хранит до четырёх уникальных ID, переживает перезагрузку и обрабатывает повреждённое или недоступное localStorage.
- Таблица показывает проверяемые поля автомобиля; отсутствующие значения явно помечены; скрытые, снятые и не принадлежащие публичной выдаче объявления не раскрываются.
- Сохранить горизонтальную прокрутку и клавиатурную доступность на узких экранах.

**Приёмка:** 0/1/2/4/5 объявлений, дубли, удаление/очистка, перегрузка, повреждённое/недоступное хранилище, мобильная таблица и публичность ID.

### 3. Полезная пустая выдача и возврат через уведомления — координатор зоны `search_and_notifications`

**Файлы:** `web/src/components/search-results.tsx`, `web/src/components/search-results.test.tsx`, `web/src/lib/search-state.ts`, `web/src/lib/search-state.test.ts`, `web/src/components/saved-search-action.tsx` и его tests; при обнаруженном дефекте — только saved-search части `backend/app/api/saved_searches.py`, `backend/app/notification_service.py`, `backend/app/worker.py`, а также `backend/tests/test_saved_searches.py` и `backend/tests/test_saved_search_notifications.py`.

- Отличать успешную выдачу без совпадений от недоступности каталога. Объяснить, что фильтры применяются совместно, и предложить несколько конкретных ссылок, ослабляющих по одному выбранному фильтру. Каждая ссылка сохраняет остальные параметры запроса, корректно сбрасывает страницу и учитывает зависимости марки/модели/региона/города.
- На пустой выдаче дать ясный путь сохранить исходный поиск и включить ежедневные уведомления в личном кабинете. Не обещать мгновенную или email-доставку без подтверждённо доступного канала.
- Проверить текущий путь создания подписки → матчинг только новых публичных объявлений после подписки → дедупликация/ежедневный дайджест → inbox delivery → пауза/изменение поиска и глобальные preferences. Не добавлять модель, миграцию или новый канал.
- Проверить, что страницы настроек уведомлений и PRO/продвижения не противоречат фактическим возможностям. PRO/оплата не являются частью этой реализации.
- Уведомления о снижении цены добавлять только при наличии безопасного существующего события и контракта; если это требует изменения модели/миграции или несогласованной общей схемы, зафиксировать как зависимость следующей очереди.

**Приёмка:** пустое состояние отдельно от сбоя; адресные relaxation links сохраняют запрос; гость возвращается после входа к тому же поиску; подписка создаётся только по явному согласию; повторная обработка не дублирует уведомление; отключённые preferences/пауза/непубличные объявления блокируют доставку. Функциональные тесты запускаются после сохранения изоляции тестовой БД.

## Зависимости и интеграция

- Владельцы работают только в назначенных файлах. Владелец фидов подтвердил, что `backend/app/worker.py` не входит в его текущий пакет; saved-search worker принадлежит зоне 3.
- Зоны 1–3 не делят исходные файлы; изменения в `listing-card.tsx`/`listing-detail.tsx` остаются у сравнения, а empty-state — у зоны 3. Общие стили/типы/API и generated файлы проходят через координатора последовательно.
- Целевая верификация web выполняется координатором после интеграции сравнения и пустой выдачи: `cd web && corepack pnpm test`, затем `corepack pnpm typecheck`. Полные web проверки не запускать параллельно.
- Backend tests не направлять на preview или runtime БД. Если подходящая disposable БД не настроена, сообщить, что integration delivery не была запущена; не считать чтение кода полноценным runtime proof.

## Метрики успеха для последующего измерения

Это определения для будущего baseline, а не утверждение, что события уже собираются:

- **Доля пустых выдач:** успешные поиски с `total = 0` / все успешные поиски.
- **Пустая выдача → ослабление / сохранение:** сессии с переходом по relaxation link или созданием saved search в течение 5 минут / сессии с пустой выдачей.
- **Сравнение → контакт:** сессии с раскрытием контакта после открытия сравнения / сессии сравнения.
- **Успешная доставка → возврат:** доставленные saved-search inbox уведомления / due delivery jobs; отдельно — сессии, начавшиеся переходом из уведомления.
- **Свежесть фида / сбои синхронизации:** время с последнего успешного применения на активный feed; failed и partial runs / все завершённые runs.

Для каждого показателя сначала проверить наличие и пригодность события/логов. Не придумывать baseline и не добавлять аналитику в эту очередь без отдельного согласования контрактов и приватности.
