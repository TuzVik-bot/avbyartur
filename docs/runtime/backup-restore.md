# Backup and Restore

## Backup

Run `make backup` while the API and database are running. By default, the output is under `$HOME/avtorinok-backups`, outside the repository and web root. Choose a protected separate filesystem with `AVTORINOK_BACKUP_DIR=/path/to/private-backups make backup` when one is available. `scripts/daily-backup.sh` applies seven-copy retention after a successful backup. Check free space first; the earlier 49 GB host inventory is historical, and the 2026-09-30 preflight measured about 72 GiB free on the current 99 GiB filesystem.

Each backup directory contains:

- `database.dump`: PostgreSQL 17 custom-format logical dump.
- `private-media.tar.gz`: the private photo volume, read through the API container.
- `catalog.json` and `catalog-coverage.json`: the seed used by that app release.
- `drom-batch-01-1-10-makes.csv` and `drom-batch-01-1-10-makes-report.json`: the owner-authorized first Drom batch and its import report.
- `drom-batch-02-10-makes.csv`, `drom-batch-02-10-makes.json`, and `drom-batch-02-10-makes-report.json`: the owner-authorized second Drom batch, its normalized data, and its import report when supplied as a complete set.
- `drom-batch-03-10-makes.csv`, `drom-batch-03-10-makes.json`, and `drom-batch-03-10-makes-report.json`: the owner-authorized third Drom batch, its normalized data, and its import report when supplied as a complete set.
- Batches 4–9 each add a CSV, normalized JSON, and report. They are backed up only as the complete six-batch group alongside the complete batch 1–3 set.
- `manifest.txt` and `SHA256SUMS`: format metadata and file checksums.

Snapshots record the exact image reference and immutable Docker image ID for each running API, worker, and web Compose container. A stopped or absent service is recorded as `unavailable`; the metadata does not infer a release from a potentially stale tag in `.env`. Version 1 is the historical five-file set with no licensed inputs. Version 2 adds the batch 1 CSV and report. Version 3 adds the batch 2 CSV, normalized JSON, and report alongside batch 1. Version 4 adds the batch 3 CSV, normalized JSON, and report alongside batches 1 and 2. Version 5 adds batches 4–9, each with CSV, normalized JSON, and report, for 26 Drom artifacts across batches 1–9. Each batch must be supplied as a complete safe set; batch 3 requires batch 2, and version 5 requires the complete batch 1–9 sequence. Restore and offsite validation require the exact checksum file set for the declared version, so version-1 through version-5 snapshots remain readable and verifiable.

The backup root is created under `umask 077`; each backup directory is mode `700` and its files are mode `600`. The Drom material is proprietary and permissioned; carrying it in a restricted backup supports the authorized owner workflow and does not grant public redistribution rights. Restrict access to local and off-host copies accordingly. The script does not include `.env`, Basic Auth handoff files, host Nginx credentials, or the Docker images themselves. Seven local copies protect against operator error but not disk loss. `scripts/backup-offsite.sh --encrypted-bundle` can transfer a locally encrypted age bundle only after an explicit invocation; `make backup` and the daily timer do not initiate that transfer. The seven-copy local retention does not prune `.tar.age` bundles or remote files. Retain the corresponding image artifacts or source release separately.

## Restore

To decrypt an age bundle, first use `scripts/backup-decrypt.py` as documented in [off-host-backup.md](off-host-backup.md). It publishes a new snapshot directory only after validating the age stream, safe archive paths/types, manifest, and checksums. This step does not call `restore.sh` or modify the application.

Restore is destructive to the active database and requires the explicit `--yes` flag. Use code compatible with the backup's schema and PostgreSQL 17. The script verifies the version-specific checksum set, creates a pre-restore backup first, stops app services, restores the DB in one transaction, restores photos into a new volume, switches `.env` to that volume, restores the catalog snapshot, and runs the catalog importer. If all 26 supported local Drom artifacts are absent, the pre-restore snapshot uses the explicit version-1 set so recovery can proceed; a normal backup still requires the batch 1 pair, and partial batches or missing preceding batches are errors. Version 2 restores the batch 1 CSV and report into `data/licensed/` with mode `600`; version 3 restores the five batch 1–2 artifacts; version 4 restores the eight batch 1–3 artifacts; version 5 restores all 26 artifacts from batches 1–9. These restores preserve unrelated licensed inputs; a version-1 restore leaves `data/licensed/` unchanged. Immediately before invoking `pg_restore`, the exit trap marks the database commit as possible. If restore is incomplete after that marker, the trap leaves web, API, and worker stopped and does not auto-restart them, to avoid serving mismatched data. Failures before the marker retain the prior behavior of restarting services that were running before restore. Inspect the database, catalog, `.env`, and Compose status before starting services manually. The new and prior media volumes and pre-restore backup are retained for recovery.

```sh
./scripts/restore.sh --yes /path/to/avtorinok-YYYYMMDDTHHMMSSZ
```

After restore, check `docker compose ps`, `docker compose logs --tail=100 api worker web`, `http://127.0.0.1:8080`, and the app's authenticated photo flow through the host Nginx proxy.
